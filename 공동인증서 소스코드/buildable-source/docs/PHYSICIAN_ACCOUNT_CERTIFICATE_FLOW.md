# 원격판독의사 직접 가입·공동인증서 로그인·판독문 서명

요구사항 갱신: 2026-10-17. 이후 요청에 따라 공급업체 SDK는 개발 범위에서 제외했다. INVIZ 영속 의사 계정·가입 재개·인증서 검증 연결과 화면을 추가했다. SDK 없이 공개 인증서와 외부 서명 결과를 검증하며, 아래 초기 차이 분석보다 [직접 가입 API·현재 구현](../apps/backend/docs/PHYSICIAN_ACCOUNTS.md)을 우선한다.

## 의사가 사용하는 흐름

1. **INVIZ 직접 가입**: 의사가 ID, 비밀번호, 이름, 연락처, 소속, 의사면허번호를 입력한다. 전문의는 자격번호와 전문과목을 추가한다. 가입 정보와 동의를 저장하고 가입 절차를 이어갈 수 있는 제한된 상태로 만든다.
2. **보유 공동인증서 등록**: 의사가 인증기관에서 이미 발급받은 공동인증서를 PC 보안프로그램에서 선택한다. 비밀번호는 해당 프로그램에 입력한다. INVIZ가 만든 일회성 요청에 서명하여 인증서에 대응하는 개인키의 소유를 증명한다. 인증서 파일을 제출하거나 이름만 비교하는 것으로 완료하지 않는다.
3. **계정과 본인·자격 연결**: 서버가 서명, 신뢰체인, 용도, 유효기간, 폐지 상태를 확인한다. 인증서 소유자와 가입자의 신원이 연결되었는지, 면허·전문의 자격과 소속이 확인되었는지 검토한다. 본인확인·자격 검토와 필요한 동의가 완료되면 의사 계정을 활성화한다.
4. **공동인증서 로그인**: 매번 새로운 일회성 요청에 서명하고 등록된 계정·인증서 상태를 확인하여 INVIZ 로그인 세션을 발급한다. 활성화 전에는 가입 현황 확인 등 허용된 기능만 사용한다. 비밀번호만으로 판독·서명 권한을 얻지는 않는다.
5. **PACS 판독**: 활성 의사 계정과 PACS 계정을 신뢰할 수 있는 서버 간 절차로 연결하고 해당 기관의 판독 권한을 확인한다. 연결된 PACS가 INVIZ 인증 결과를 검증한 뒤 업무 세션을 발급한다.
6. **최종 승인과 전자서명**: 의사가 완성된 판독문을 확인하고 최종 승인한다. 서버는 의사·기관·권한·문서 버전·원문 해시와 승인을 검증한 뒤 OpenBao의 의사별 키로 서명한다. 서명값, 검증에 필요한 공개 인증서와 키 버전, 원문 해시, 승인자, 승인 시각 및 감사기록을 연결해 보존한다.

가입 화면의 시작점은 기존 PACS 계정을 필수로 요구하지 않는 INVIZ 직접 가입이다. 기존 PACS 계정에서 시작하는 등록도 지원하되 두 경로는 동일한 Doctor ID와 인증서 관리 체계로 합쳐야 한다. 가입자가 입력한 면허번호나 이름만으로 기존 PACS 계정에 자동 연결하지 않는다.

## 인증과 판독문 서명의 역할

| 구분 | 사용하는 키 | 목적 |
|---|---|---|
| 공동인증서 등록·로그인 | 의사 PC의 외부 공동인증서 개인키 | 인증서 소유 확인과 INVIZ 계정 인증 |
| 판독문 전자서명 | OpenBao에 관리되는 INVIZ 의사별 개인키 | 의사가 최종 승인한 판독문에 대한 서명 |

이 구조는 앞서 정한 OpenBao 설계를 유지한다. 외부 공동인증서로 판독문 자체를 서명하는 것과는 다른 방식이다. 외부 공동인증서를 판독문 서명에도 사용하도록 변경하려면 문서별 승인 시 PC에서 해당 키로 서명하거나 인증기관의 원격서명 서비스를 연동해야 한다.

문서 작성 중 자동 저장은 서명 행위가 아니다. 최종 승인된 내용이 변경되면 기존 서명을 덮어쓰지 않고 새로운 문서 버전과 새 승인을 생성해야 한다. 로그인 성공만으로 모든 문서의 승인이 이루어진 것으로 취급하지 않는다.

## 구현 범위

| 기능 | 현재 상태 | 추가 작업 |
|---|---|---|
| INVIZ 의사 직접 가입 | 새 영속 계정 API와 화면을 기존 Doctor ID에 연결 | 기존 일반 개인 SMS 가입과 구분, 가입 전용 세션 적용 |
| 기존 PACS 계정의 직접 인증서 등록 | 서버 간 인증 후 등록 시작, 초대코드 미사용 | 유지하며 신규 INVIZ 계정과의 명시적 연결 절차 추가 |
| 공급업체 보안프로그램 | 이번 개발 범위에서 제외 | 공개 인증서와 외부 서명 결과 제출로 서버 검증 수행 |
| 공동인증서 검증·로그인 | 일회성 요청, 원문 서명, 신뢰체인·CRL 검증과 의사 세션 구현 | 운영 CA·폐지 확인 구성 및 공급업체 서명 형식 호환 검증 |
| 의료인 자격 | 직접 가입에도 면허·전문의 정보 제출과 기관 담당자 검토 필수 | 입력 번호만으로 검증 완료하지 않음 |
| 판독문 승인·서명 | 의사 승인 화면, 문서 해시 검증, OpenBao 서명 및 PACS 연동 구현 | 신규 직접 가입 계정으로 전체 흐름을 검증하고 실제 PACS 환경에 적용 |

일반 개인 가입은 `EnrollmentService`, 의사 직접 가입은 `PhysicianAccountService`, 의사 계정과 인증 세션은 `DoctorService`, 외부 인증서 등록·로그인은 `CertificateEnrollmentService`에서 처리한다. 일반 가입의 메모리 계정을 그대로 인증서 계정으로 간주하지 않는다. 의사 직접 가입은 기존 영속 Doctor ID와 연결해야 서버 재시작, 다중 인스턴스, 정지·폐지 시에도 상태가 일치한다.

## 직접 가입 처리 원칙

1. 영속 계정에 로그인 ID의 고유성, 비밀번호 해시, 가입 경로, 연락처, 가입 동의와 Doctor ID 연결을 저장한다. 계정 생성과 증빙 소유권을 서버에서 관리하고 기관·역할을 입력값만으로 부여하지 않는다.
2. 가입 절차 전용 세션을 발급한다. 이 세션은 본인의 인증서 등록과 가입 현황 확인에만 사용하고 판독·승인 API에서는 거절한다. 가입 요청에는 시도 제한과 만료·재시도 처리를 적용한다.
3. 가입 계정에 묶인 인증서 등록 요청을 발급하고 실제 소유 증명 뒤에 연결한다. 다른 계정에 연결된 인증서는 자동 재할당하지 않는다. 가입 정보의 이름·면허번호와 인증서 이름의 일치만으로 신원 검증을 완료하지 않는다.
4. 기존 의료인 자격·동의·검토 절차를 신규 계정 경로에도 연결한다. 연락처를 입력만 받은 경우에는 검증 완료로 표시하지 않는다. 연락처 확인과 인증서 본인확인은 별도 상태로 관리한다.
5. 활성화된 계정의 인증서 로그인과 PACS 계정 연결을 통합한다. 정지·폐지·인증서 갱신 시 기존 세션과 서명 권한도 함께 재검증한다.
6. 신규 가입부터 실제 인증서 로그인, 기관별 PACS 연결, 최종 판독 승인과 서명 검증까지 시험한다. 미활성 계정, 다른 사용자·기관, 요청 재사용, 폐지 인증서와 문서 변경 요청은 거절되는지 확인한다.

공급업체 SDK는 이번 구현의 선행조건이 아니며 연동하지 않는다. 기존 [공급업체 요청서](CERTIFICATE_VENDOR_RFI.md)와 [업체 검토](CERTIFICATE_VENDOR_SELECTION.md)는 향후 필요할 때 참고한다. 현재는 공개 인증서와 외부 서명 결과를 기존 검증 API로 제출한다.
