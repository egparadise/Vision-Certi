# Vision Certi 구현 계획

인비즈 중앙 서버에서 다기관 의사 인증, 전자서명, 인증서 수명주기, 서명 검증과 병원 전송을 관리한다. Claude는 백엔드, antigravity는 프런트엔드, Codex는 DB와 공통 계약·인프라·통합 검증을 담당한다.

이 문서 묶음은 개발 착수 기준이다. 문서 작성 완료가 프로그램 구현·보안 검증·인증 취득 완료를 뜻하지 않는다. 작업 상태는 [[06_작업분해_의존성]]에서 관리한다.

## 확정한 제품 범위

| 항목 | 결정 |
|---|---|
| 1차 제품 | 원격판독 인증·서명 서버, 관리자 콘솔, 의사 서명 전용 화면, 권한 있는 검증 포털 |
| 의사 업무 | 기존 Cloud Care/PACS에서 작성한 판독문을 확인하고 건별 승인·서명 |
| 제외 | 영상 뷰어, 판독문 편집기, 환자·보호자 동의, 일괄서명, 국가 인증 취득 절차 |
| 배포 | 인비즈 중앙 Linux 서버, 다기관 지원 |
| 기술 | Java 21·Spring Boot 4 계열, React·TypeScript·Vite, PostgreSQL 18 |
| 초기 용량 목표 | 100개 기관, 의사 1천 명, 일 10만 건, 피크 초당 50건 접수 |
| 외부 연동 | 공급자 미정. 어댑터·모의 서버 개발 후 실제 공급자 계약 시험 |
| 정상 UX | 로그인 시 MFA, 문서 확인 후 최종 판독·서명 버튼 1회, 위험 시에만 Step-up |

수치와 기술 선택은 제품 설계 기본값이며 실측 성능 또는 법적 의무 수치가 아니다. 병원 계약·공급자 제약으로 변경할 때 결정대장과 관련 계약·시험을 함께 갱신한다.

## 읽는 순서

인증 완료 후 흰 창의 원인과 수정·직접 검증 결과는 [[2026-10-22_PACS_인증완료_흰창_수정]]을 확인한다.

현재 PACS 공동인증서 파일 서명 구현과 운영 시험 범위는 [[2026-10-17_PFX_NPKI_공동인증서_직접서명_연동]]을 우선 확인한다.

1. [[01_원문분석_요구사항추적표]]에서 원문과 구현 범위를 확인한다.
2. [[02_아키텍처_보안경계]], [[03_DB_데이터사전]], [[04_API_연동계약]]을 공통 계약으로 읽는다.
3. 화면 담당자는 [[05_화면_사용자흐름]]을 읽는다.
4. [[06_작업분해_의존성]]에서 선행 작업이 완료된 티켓만 시작한다.
5. 담당별 [[07_Claude_백엔드_작업지시]], [[08_antigravity_프런트엔드_작업지시]], [[09_Codex_DB_인프라_통합계획]]을 사용한다.
6. [[10_테스트_출시_운영]]으로 완료를 판단하고 [[11_외부의존성_결정대장]]으로 운영 차단 조건을 관리한다.

## 책임과 변경 절차

| 담당 | 단독 소유 영역 | 다른 담당에게 요청할 사항 |
|---|---|---|
| Claude | apps/backend, 백엔드 단위·서비스 통합 테스트 | DB 변경·OpenAPI 변경은 Codex에 요청 |
| antigravity | apps/web, UI 단위·브라우저 테스트 | API 신규 요구·오류 코드 추가는 Codex에 요청 |
| Codex | contracts, database, infra, tests/integration, tests/security, tests/load, docs | 비즈니스 로직 변경은 Claude, 화면 변경은 antigravity와 조율 |
| 인비즈 책임자 | 공급자·병원 계약, 실제 신원 심사 운영, 법무·보안 검토, 출시 승인 | 개발자에게 운영 증거·시험 결과 요청 |

계약 변경 요청에는 이유, 요청 필드·상태, 기존 동작 영향, 마이그레이션, 시험을 적는다. Codex가 계약을 갱신하면 Claude와 antigravity가 동일 버전에 맞춘다. 공급자 선택이나 법적 판단을 에이전트가 확정한 사실처럼 기록하지 않는다.

## 단계별 출구 조건

| 단계 | 제품 결과 | 다음 단계 진입 조건 |
|---|---|---|
| P0 | 계약·ERD·위협모델·개발환경·모의 API | 공통 계약 검증과 개발환경 부팅 |
| P1 | 기관·의사 심사·MFA·세션·권한 | 기관 간 접근 차단, 권한 철회 즉시 적용 |
| P2 | 고정 원본부터 승인·서명·증거·검증까지 | 모의 외부 시스템에서 수직 흐름과 실패 시험 통과 |
| P3 | 인증서 수명주기·전송·감사 화면 | 폐기·재전송·중복·정정 처리 통과 |
| P4 | 실제 공급자 통합·부하·복구·출시 심사 | 운영 차단 항목 해소, 실제 시험 및 인간 승인 |

최초 실행 순서는 ARCH-001 → API-001/DB-001/INF-001이다. 이후 백엔드와 화면 골격을 병렬 개발한다. 공급자 도입·병원 협의 기간은 개발 기간과 분리하며 근거 없는 납기를 약속하지 않는다.

## 저장소와 문서 기준본

최근 운영 배포 보고: [[2026-10-20_PACS_인증서확인_운영배포_보고]].

개발 작업 폴더는 `C:\Project\Vision-Certi`이다. Obsidian 문서는 사용자 지정 폴더에 보관한다. 앞으로 작성할 실행 가능한 OpenAPI·DDL·배포 설정의 기준본은 코드 저장소이며, 이 문서 묶음은 그 구현 의도와 작업 지시다. 실제 구현이 바뀌면 코드와 설명을 같은 변경 건에서 갱신한다.

문서 원본은 두 PDF이고, 출처·페이지·관련 공식 자료는 [[01_원문분석_요구사항추적표]]에 기록한다. 실제 환자정보, 운영 토큰, 키, HSM PIN은 Obsidian·OneDrive·소스 저장소에 보관하지 않는다.
