# 공동인증서 공급업체 검토와 연동 계획

기준일: 2026-10-17. 상태: 공급업체 미정, 평가 SDK·라이선스 미수령, 문의 미발송.

후속 결정: SDK 연동은 현재 개발 범위에서 제외한다. 아래 업체 검토는 참고자료이며 가입·계정·인증서 검증·서명 개발의 선행조건이 아니다. [현재 구현](../apps/backend/docs/PHYSICIAN_ACCOUNTS.md)을 따른다.

## 우선 검토 후보

한국전자인증의 **CrossCert 웹표준 공동인증 모듈**을 먼저 기술 검토하고, 드림시큐리티의 **Magic Line for Web**을 비교 후보로 검토한다. 계약이나 제품 선정을 확정한 것은 아니다. 설치형 보안프로그램과 웹 화면을 연결하려는 현재 요구에 대한 검토 순서이며, 실제 SDK 호환성과 견적을 확인한 뒤 결정한다.

| 후보 | 공식 설명에서 확인한 기능 | 우리 프로그램과 연결하기 전 확인할 사항 |
|---|---|---|
| 한국전자인증 CrossCert 웹표준모듈 | JavaScript/HTML5 클라이언트, NIM 실행파일, 저장매체 접근, 서명 검증 및 인증서 경로·OCSP·CRL 지원 | 현재 공급 제품명·버전, Windows/Chrome/Edge 지원, 원문 서명 API, Java 서버 모듈, PACS 배포 라이선스 |
| 드림시큐리티 Magic Line for Web | 인증서 전자서명, PKCS#7 SignedData, 여러 저장매체, HTML5 무설치 방식 | PC 저장 인증서에 접근하는 구성, 설치형 옵션, 원문 서명 지원 여부, CMS 서버 검증 범위, Electron 지원 |

제품 기능의 근거: [한국전자인증 제품 구성](https://www.crosscert.com/solution/03_1_07_2.jsp), [드림시큐리티 제품 설명](https://www.dreamsecurity.com/product/access/line-for-web%E2%80%8B). 공급업체 설명은 우리 프로그램에서 검증한 결과가 아니다. 제품명·지원 버전·공급 범위는 회신으로 확정한다.

공식 문의 경로는 [한국전자인증 제품 구매문의](https://www.crosscert.com/solution/03_5_01.jsp)와 [드림시큐리티 제품 문의](https://www.dreamsecurity.com/product/access/line-for-web%E2%80%8B)이다. 전달용 초안은 [기술·견적 요청서](CERTIFICATE_VENDOR_RFI.md)에 별도로 작성했다.

## 도입 범위와 의료인 확인

공급업체 모듈의 범위는 의사 PC에 보관된 공동인증서를 선택하고, PC 안에서 비밀번호를 입력하여 서버의 일회성 요청에 서명하는 것이다. INVIZ는 공개 인증서, 인증서 체인, 서명값을 검증하여 PACS 계정에 연결한다. 일반 설치 프로그램을 내려받는 것만으로 웹 SDK 연동이나 이용 라이선스가 확보되지는 않는다.

최종 목표는 `INVIZ 직접 가입 → 보안프로그램 확인·설치 → 보유 공동인증서 선택·서명 → 계정·의료인 자격 연결 및 동의·검토 → 활성화 → 공동인증서 로그인 → 최종 판독 승인·전자서명`이다. 현재 구현된 등록 시작점은 기존 PACS 계정 확인이며, INVIZ 직접 가입 연결은 추가 작업이다. 두 경로 모두 관리자 초대코드를 사용하지 않는다. [직접 가입 목표와 구현 차이](PHYSICIAN_ACCOUNT_CERTIFICATE_FLOW.md)를 기준으로 연결한다.

의사면허번호와 전문의 자격번호 입력만으로 자격 검증을 완료하지 않는다. 현재 구현은 신뢰할 수 있는 PACS 계정 정보와 입력 내용을 대조하고, 기관 담당자가 인증서 소유자·의사 신원·면허·자격 증빙을 검토하는 방식이다. 인증서 소유 증명과 의료인 자격 확인은 별개이며, 공급업체의 공동인증 모듈이 면허 조회 기능까지 제공한다고 가정하지 않는다. 자동 자격 조회를 도입하려면 제공기관, 접근 권한, 본인 연결 근거, 응답 명세를 별도로 확보해야 한다.

판독문은 의사의 문서별 승인 후 OpenBao의 의사별 키로 서명한다. 로그인에 사용한 외부 공동인증서로 판독문을 직접 서명하는 구조는 아니다.

## 현재 코드와 공급업체의 연결 지점

| 영역 | 현재 구현 | 공급업체 자료 확보 후 작업 |
|---|---|---|
| 보안프로그램 UI | 설치 확인, 인증서 선택, 서명 요청 화면 | 공식 SDK 로더와 설치파일 배포 연결 |
| 브라우저 어댑터 | `apps/web/src/services/localCertSdkAdapter.ts` | 공식 API를 `isAvailable`, `getCertificates`, `signChallenge`에 매핑 |
| 설치 메타데이터 | `apps/web/.env.certificate.example` | 프로그램 이름, 승인된 HTTPS 다운로드 주소, SHA-256 설정 |
| 인증서 검증 | Java 원문 서명·신뢰체인·설정된 CRL 검증 | 지원 인증서 정책, 운영 CA·폐지 검증 경로 및 필요 서버 모듈 연결 |
| PACS 연결 | 서버 간 계정 연결, 브라우저 인증, 인증서 세션 | 실제 PACS origin과 배포 환경에서 등록·로그인 확인 |

`window.pcCertSdk.isReady/listCerts/sign`은 INVIZ 내부 연결 규약이다. 특정 공급업체가 이 이름으로 API를 제공한다는 의미가 아니다. 실제 SDK 문서를 받아 매핑한다.

### 서명 형식 확인

현재 어댑터는 서버가 만든 `dataToSignBase64`의 정확한 바이트를 서명하도록 요청한다. 반환 계약은 다음과 같다.

```typescript
interface LocalSignResult {
  certificateDerBase64: string;
  chainDerBase64: string[];
  signatureBase64: string;
  signatureAlgorithm: string;
  fingerprintSha256: string;
}
```

현재 서버 검증 알고리즘은 `SHA256withRSA`, `SHA256withECDSA`이다. 문자열 인코딩 변환, 줄바꿈 변경, 사전 해시 여부, RSA 패딩과 ECDSA 서명 인코딩을 샘플로 확인해야 한다.

SDK가 PKCS#7/CMS SignedData만 반환하면 현재 `signatureBase64`에 그대로 넣지 않는다. CMS의 서명 속성·메시지 다이제스트·실제 서명자와 인증서·원문 결합을 검증하는 서버 처리가 필요하다. 단순히 CMS에서 서명값을 추출하는 변환으로 호환된다고 판단하지 않는다.

개인키, PFX/PKCS#12 파일, 인증서 비밀번호와 PIN은 INVIZ 웹 앱이나 서버에 전달하지 않는다. 비밀번호 입력과 개인키 사용은 공급업체 보안모듈 안에서 처리한다.

### 신뢰체인과 폐지 확인

현재 검증기는 설정된 신뢰 앵커와 CRL을 사용하며, 인증서가 제시하는 주소로 자동 접속하지 않는다. 공급업체 제품의 OCSP 지원 설명만으로 INVIZ에 OCSP가 연결된 것으로 간주하지 않는다. OCSP 도입 시 응답자 권한·서명·인증서 식별·유효 시각 검증, 허용 통신 대상, 장애 시 처리까지 구현·검증한다. 폐지 상태를 확인할 수 없는 인증서를 성공 처리하지 않는다.

## 자료 수령 이후 작업 순서

1. 공식 SDK·서버 모듈·평가 라이선스와 재배포 조건을 확인하고 설치파일의 서명·해시를 검증한다. 비공개 SDK와 라이선스는 공개 저장소에 커밋하지 않는다.
2. 샘플로 인증서 목록 및 일회성 요청 서명을 실행하여 원문 바이트와 반환 형식을 확인한다. CMS 전용이면 서버 변경 범위를 먼저 확정한다.
3. 공급업체 로더·어댑터를 연결하고 실제 프로그램 응답에 따라 설치 상태를 표시한다. 설치 완료나 인증 성공을 임의로 생성하지 않는다.
4. 운영에 사용할 CA·인증서 정책과 폐지 확인 경로를 설정한다. 개발용 CA로 수행한 검증과 실제 공동인증서 검증 결과를 구분한다.
5. 현재 내부망 INVIZ 주소 `https://100.68.224.44:5184`와 실제 PACS 주소를 이용해 시험한다. 공급업체에 사설 IP·개발 도메인 라이선스, HTTPS, 최신 브라우저의 로컬 통신 권한 요구를 확인한다. 운영 도메인은 별도 확정한다.
6. 아래 인수 기준을 통과한 제품의 견적·지원 범위로 도입을 결정한다. 공급업체 회신 전에는 실제 연동 완료일이나 금액을 확정하지 않는다.

## 인수 기준

| 항목 | 통과 조건 |
|---|---|
| 설치 및 업데이트 | 설치·재실행·업데이트 후 웹에서 실제 연결 확인, 미설치·실행 실패 시 인증 진행 차단 |
| 인증서 선택 | 허용한 저장매체의 실제 인증서 선택, 선택 지문과 반환 인증서 일치 |
| 서명 검증 | 발급한 정확한 바이트의 정상 서명 통과, 변조·다른 키·만료·재사용 요청 거부 |
| 인증서 상태 | 신뢰하지 않는 체인, 허용하지 않는 용도, 만료·폐지·상태 확인 실패 거부 |
| 의료인 연결 | 다른 PACS 사용자·기관 연결 거부, 면허 불일치 거부, 자격 정보 수정 후 이전 제출본 승인 거부 |
| 로그인 및 판독 | 직접 등록·기관 검토·활성화 후 매번 인증서 로그인, 문서별 승인과 OpenBao 서명까지 완료 |
| 정보 보호 | 비밀번호·개인키가 웹 앱, API, 로그로 전송되지 않음 |
| 실제 배포 | 목표 Windows/Chrome/Edge와 PACS 클라이언트에서 확인, Electron은 공급업체 지원 방식으로 별도 검증 |

현재 프로그램의 상세 구현과 검증 범위는 [의료인 인증서 등록](MEDICAL_CERTIFICATE_ONBOARDING.md), [PACS 직접 등록 API](../apps/backend/docs/PACS_SELF_ENROLLMENT.md)를 참고한다.
