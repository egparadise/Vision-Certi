# PACS 공동인증서 검증 경로 수정

운영 PACS 인증 화면은 `CERTIFICATE_UNTRUSTED`와 함께 신뢰 기관까지 경로를 만들 수 없다고 표시했다. PC의 공개 인증서와 YESKEY의 현재 `yessignCA Class 3` 공개 CA를 별도로 검사하니 발급 서명과 키 식별자가 일치했다. 운영 Secret Manager에 보관된 CA의 SHA-256 지문도 YESKEY 디렉터리의 공개 CA와 일치했다.

동일 인증서로 Java PKIX 경로 빌드를 재현한 결과, 기본 설정이 critical `certificatePolicies` 안의 CPS·UserNotice qualifier를 거절했다. 인증서의 정책 안내를 CPS URI·UserNotice 형식으로 확인한 뒤 허용하도록 `CertificateValidator`를 수정했다. 암호 확인만으로 CA·유효기간·폐지 검증을 생략하지 않는다.

추가로 운영 CRL의 critical `issuingDistributionPoint`가 인증서의 CRL 배포 지점과 같은 주소를 가리키는 것을 확인했다. 수정된 검증기는 양쪽 full name이 정확히 일치하고 이유 범위·간접 발급기관 제한이 없을 때만 해당 CRL을 적용한다. 다른 배포 지점, 부분 이유 범위, 간접·델타 CRL은 계속 거절한다. 실제 공개 인증서는 해당 CRL의 폐지 목록에 없고, 발급기관 서명과 갱신 시각은 유효했다.

회귀 테스트 `CertificatePolicyQualifierTest`, `CertificateRevocationScopeTest` 및 관련 PACS 인증서 확인 테스트를 통과했다. Cloud Run `vision-certi-api-00012-crn`이 이미지 `sha256:34dadd24607016f1f0a1cca123c1459e38e785723699a6eec9a35164b24e21d9`로 준비 완료됐다. 공개 capabilities는 PostgreSQL `READY`, CRL `FRESH`, PACS 통합 사용 가능을 반환하고, PACS 일회용 challenge 생성은 HTTP 201이다.

의사 PC의 인증서 비밀번호를 입력해 PACS 로그인까지 마치는 종단 간 확인은 아직 수행하지 않았다. PACS 로컬 브로커의 HMAC 코드 교환 설정도 별도 확인이 필요하다. 운영 API의 `clinicalUseAllowed`는 계속 `false`다.
