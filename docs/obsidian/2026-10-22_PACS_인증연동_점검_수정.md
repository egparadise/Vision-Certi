## 보고만 하는 사항(코드를 바꾸지 않음)

1. **접속지별 challenge 제한의 키.** 공개 challenge 경로(`/v1/pacs-certificate-proofs/challenges` 등)는 `request.getRemoteAddr()` 기준으로 기본 30회/시간을 제한한다. 운영 API는 Firebase Hosting과 Cloud Run 프런트엔드 뒤에 있고 `server.forward-headers-strategy`가 설정되어 있지 않아, 컨테이너가 보는 원격 주소가 프록시 주소일 가능성이 높다. 그러면 **모든 의사가 한 버킷(30회/시간)을 공유**해 `CHALLENGE_RATE_LIMITED`(429, "인증 요청이 너무 많습니다")가 난다. 배포 없이는 확인할 수 없어 코드를 바꾸지 않았다. 즉시 조치는 관리자 모드의 `doctor.source-challenge-hourly-limit`(최대 1,000) 상향, 근본 조치는 `X-Forwarded-For` 신뢰 범위를 정한 뒤 실제 값을 확인하는 것이다.
2. **PACS 3.40.5의 남은 `popup.close()` 경로.** 성공 경로만 창을 유지한다. PACS ID/PW 실패, 5분 시간 초과, 연동 설정 조회 실패에서는 여전히 `popup.close()`를 호출해 같은 흰 창이 남을 수 있다. 근본 수정은 Rust 셸에서 팝업 WebView의 `WindowCloseRequested`를 받아 Tauri 창을 `destroy()`하는 것이다. `work/pacs-completion-fix`에는 커밋되지 않은 실험(`certificate:show-complete` 네이티브 완료창, `certificate-complete.html`)이 진행 중이다.
3. **이 PC의 PACS는 3.40.4 그대로다.** 3.40.5 설치 파일은 배포됐지만 설치되지 않았다. 이 PC에서 흰 창 현상은 설치 전까지 계속된다.
4. **PACS 설정의 인증 서버 주소 선택지**(`CERTIFICATE_SITE_OPTIONS`)에 옛 주소 `https://hahattalk-vision-certi.web.app`가 남아 있다. 제거하거나 `LEGACY_CERTIFICATE_URLS`에 넣어 정규화해야 한다.
5. **동시 작업.** 점검 중 다른 작업자가 같은 작업 트리에서 `firebase.json`, `infra/cloud/README.md`, `infra/cloud/Check-WebDeployment.cjs`, `tests/browser/native-completion.cjs`와 보고서 [[2026-10-22_두_웹배포_점검과_PC_완료창]]을 작성하고(미커밋), `work/pacs-completion-fix`의 PACS 클라이언트(3.40.6 작업)를 11:46에 다시 빌드했으며 11:57에 PACS를 실행했다. 그 파일과 실행 중인 PACS는 건드리지 않았고, 그래서 실기기 검증(`native-completion.cjs`)도 수행하지 않았다. 그쪽 보고서에 따르면 옛 주소 사이트에 남아 있던 이전 빌드는 **이 점검의 웹 빌드(12:03) 이전 시점의 `dist`로 이미 재배포**됐다. 따라서 지금 저장소의 `apps/web/dist`(이번 수정 포함)는 아직 배포되지 않았고, `Check-WebDeployment.cjs`를 다시 돌리면 불일치로 나온다. 3.40.6의 "시작 실패 시 `window.close()`로 흰 프레임을 만들지 않는다"는 방향은 6번 수정의 전제와 같다.
